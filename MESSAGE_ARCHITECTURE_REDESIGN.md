# Message Architecture Redesign - Four-Tier Message Hierarchy

**Date**: 2025-11-13
**Updated**: 2025-11-13 (Added ToolMessage 4th tier, discriminator property, testing strategy)
**Status**: ARCHITECTURAL PROPOSAL
**Purpose**: Design stable, extensible message architecture with clear message origin categories

---

## Executive Summary

This document proposes a **four-tier message hierarchy** that categorizes all messages by their **origin** rather than their specific type. This creates a stable orchestrator API while allowing unlimited message type extensibility within each category.

### The Four Message Origin Categories

1. **UserMessage** - Messages originating from human user input
2. **LlmMessage** - Messages originating from LLM responses
3. **ApplicationMessage** - Messages generated by application logic (scenarios, workflows, notifications)
4. **ToolMessage** - Messages originating from tool execution infrastructure (MCP servers, built-in tools)

This design ensures:
- ✅ **Stable Orchestrator API** - Only 4 processing methods, never grows
- ✅ **Unlimited Extensibility** - Add new subtypes without API changes
- ✅ **Clear Separation** - Message origin is explicit in the type system
- ✅ **Future-Proof** - New application features add subtypes, not API methods
- ✅ **Serializable** - Built-in support for polymorphic serialization via discriminator property

## Problem Statement

### Current Issue

The codebase needs to distinguish scenario-generated messages from user-typed messages for UI display, but:
1. Domain `UserMessage` has no metadata about message origin
2. Proposed solution adds `ProcessScenarioUserMessageAsync()` to orchestrator
3. **This sets a precedent**: Every new message variant = new orchestrator method
4. **Orchestrator API will grow unbounded** as features are added

### Root Cause

**Messages are categorized by their role (User/Assistant) rather than their origin (Human/LLM/App).**

Example confusion:
- Scenario sends a message with User role → `UserMessage`
- Human types a message with User role → `UserMessage`
- These have the same role but different origins!

### Why This Matters

As the application grows, we'll have:
- User messages from scenarios (teaching mode)
- User messages from tool updates
- User messages from automated workflows
- User messages from context injection
- **Each requiring different UI display and handling**

Without architectural clarity, we'll end up with:
```csharp
// ❌ API Bloat - Every variant adds a method
IAgentOrchestrator
{
    ProcessUserInputAsync()
    ProcessScenarioUserMessageAsync()
    ProcessToolUpdateMessageAsync()
    ProcessWorkflowMessageAsync()
    ProcessContextInjectionMessageAsync()
    // ... ad infinitum
}
```

## Proposed Solution: Four-Tier Message Hierarchy

### Tier 1: Message Origin (Root Types)

Four abstract base classes representing message origin:

```csharp
/// <summary>
/// Base interface for all messages with discriminator support for serialization.
/// </summary>
public interface IMessage
{
    Guid Id { get; }
    MessageRole Role { get; }
    string Content { get; }
    DateTime Timestamp { get; }
    MessageContextStatus ContextStatus { get; set; }

    /// <summary>
    /// Type discriminator for polymorphic serialization/deserialization.
    /// Format: "{OriginCategory}.{ConcreteType}"
    /// Examples: "User.Direct", "Application.ScenarioUser", "Llm.Text", "Tool.Result"
    /// </summary>
    string MessageTypeDiscriminator { get; }
}

/// <summary>
/// Messages originating from human user input.
/// Represents direct human interaction with the agent.
/// RULE: Use ONLY when user typed text, used voice input, or pasted text into chat.
/// DO NOT use for system-generated messages even if user-initiated.
/// </summary>
public abstract class UserMessage : IMessage
{
    public Guid Id { get; }
    public MessageRole Role => MessageRole.User;
    public string Content { get; }
    public DateTime Timestamp { get; }
    public MessageContextStatus ContextStatus { get; set; }
    public abstract string MessageTypeDiscriminator { get; }
}

/// <summary>
/// Messages originating from LLM responses.
/// Represents AI agent outputs.
/// </summary>
public abstract class LlmMessage : IMessage
{
    public Guid Id { get; }
    public MessageRole Role => MessageRole.Assistant;
    public string Content { get; }
    public DateTime Timestamp { get; }
    public MessageContextStatus ContextStatus { get; set; }
    public abstract string MessageTypeDiscriminator { get; }
}

/// <summary>
/// Messages generated by the application itself.
/// Represents system-driven actions, scenarios, automation, workflows, notifications.
/// NOTE: "Application" is used instead of "System" to avoid confusion with LLM system prompts.
/// RULE: Use when system translated user action into message, or application logic generated content.
/// </summary>
public abstract class ApplicationMessage : IMessage
{
    public Guid Id { get; }
    public abstract MessageRole Role { get; } // Can be User, Assistant, or other
    public string Content { get; }
    public DateTime Timestamp { get; }
    public MessageContextStatus ContextStatus { get; set; }
    public abstract string MessageTypeDiscriminator { get; }

    /// <summary>
    /// Type of application message for identification and routing.
    /// Examples: "scenario_user_message", "tool_update", "context_injection"
    /// </summary>
    public string MessageType { get; }
}

/// <summary>
/// Messages originating from tool execution infrastructure.
/// Represents results from MCP servers and built-in tools.
/// Tools are external operations (file system, git, network, etc.) - distinct from app-internal logic.
/// </summary>
public abstract class ToolMessage : IMessage
{
    public Guid Id { get; }
    public MessageRole Role => MessageRole.Tool;
    public string Content { get; }
    public DateTime Timestamp { get; }
    public MessageContextStatus ContextStatus { get; set; }
    public abstract string MessageTypeDiscriminator { get; }

    /// <summary>
    /// ID of the tool call this message is responding to.
    /// Links tool result back to the LLM's tool call request.
    /// </summary>
    public Guid ToolCallId { get; }

    /// <summary>
    /// Name of the tool that was executed.
    /// </summary>
    public string ToolName { get; }
}
```

### Tier 2: Concrete Message Types

Specific implementations inherit from their origin category:

#### User-Originated Messages

```csharp
/// <summary>
/// Standard message typed by human user in chat interface.
/// </summary>
public class DirectUserMessage : UserMessage
{
    public override string MessageTypeDiscriminator => "User.Direct";

    public DirectUserMessage(string content)
    {
        Content = content;
        Id = Guid.NewGuid();
        Timestamp = DateTime.UtcNow;
        ContextStatus = MessageContextStatus.InContext;
    }
}
```

### Tier 3: Orchestrator API (Stable)

**The orchestrator API has exactly 4 processing methods - one per origin category:**

```csharp
public interface IAgentOrchestrator
{
    /// <summary>
    /// Process a message originating from human user input.
    /// </summary>
    IAsyncEnumerable<StreamingResponseChunk> ProcessUserMessageAsync(
        UserMessage message,
        CancellationToken cancellationToken = default);

    /// <summary>
    /// Process a message originating from LLM (rare, mostly for internal use).
    /// Example: Re-processing LLM responses, message regeneration.
    /// </summary>
    IAsyncEnumerable<StreamingResponseChunk> ProcessLlmMessageAsync(
        LlmMessage message,
        CancellationToken cancellationToken = default);

    /// <summary>
    /// Process a message originating from the application itself.
    /// Examples: scenarios, tool updates, automated workflows, notifications.
    /// </summary>
    IAsyncEnumerable<StreamingResponseChunk> ProcessApplicationMessageAsync(
        ApplicationMessage message,
        CancellationToken cancellationToken = default);

    /// <summary>
    /// Process a message originating from tool execution infrastructure.
    /// Examples: MCP server tool results, built-in tool execution results.
    /// </summary>
    IAsyncEnumerable<StreamingResponseChunk> ProcessToolMessageAsync(
        ToolMessage message,
        CancellationToken cancellationToken = default);
}
```

**Internal routing handles subtypes:**

```csharp
public async IAsyncEnumerable<StreamingResponseChunk> ProcessApplicationMessageAsync(
    ApplicationMessage message,
    CancellationToken cancellationToken = default)
{
    // Add message to conversation
    _conversationManager.AddMessage(message);

    // Route based on specific message type
    switch (message)
    {
        case ScenarioUserMessage scenarioMsg:
            // Scenario-specific handling if needed
            LogEvent("ScenarioMessage", $"Processing scenario: {scenarioMsg.Annotation}");
            break;

        case ToolUpdateMessage toolUpdate:
            // Tool update specific handling
            LogEvent("ToolUpdate", $"Added: {string.Join(", ", toolUpdate.AddedTools)}");
            break;

        // Future message types handled here
        default:
            LogEvent("ApplicationMessage", $"Processing: {message.MessageType}");
            break;
    }

    // All application messages trigger same LLM processing loop
    await foreach (var chunk in ProcessStreamingToolLoopAsync(0, cancellationToken))
    {
        yield return chunk;
    }
}
```

## Key Architectural Decisions

### AD-001: Message Origin as Primary Categorization

**Decision**: Categorize messages by origin (User/LLM/Application) rather than role.

**Rationale**:
- Origin determines processing logic and UI display
- Role (User/Assistant/System) is an LLM API concept, not a domain concept
- A scenario can send messages with User role, but it's not from a human user
- Clear separation enables distinct handling per origin

**Consequences**:
- ✅ Type system enforces correct message handling
- ✅ New message types don't pollute orchestrator API
- ⚠️ More complex type hierarchy (3-tier instead of flat)

---

### AD-002: ApplicationMessage Instead of SystemMessage

**Decision**: Use "ApplicationMessage" term instead of "SystemMessage".

**Rationale**:
- "System" is overloaded in AI context (system prompts are a specific LLM concept)
- "System message" in Anthropic/OpenAI APIs refers to system prompts/instructions
- "Application" clearly indicates "generated by our application logic"
- Avoids confusion with LLM system prompt messages

**Consequences**:
- ✅ Clear terminology
- ✅ No confusion with LLM API concepts
- ⚠️ Slightly longer name

---

### AD-003: Abstract Base Classes vs Interfaces

**Decision**: Use abstract base classes for message origin categories.

**Rationale**:
- Base classes can provide shared implementation (Id, Timestamp, common properties)
- Still allows interface-based polymorphism via `IMessage`
- Reduces code duplication across message types
- Enforces common structure while allowing specialization

**Consequences**:
- ✅ Less code duplication
- ✅ Shared behavior in base class
- ❌ Can't use multiple inheritance (C# limitation)

**Alternative Considered**: Pure interfaces (`IUserMessage`, `ILlmMessage`, `IApplicationMessage`)
- Would allow more flexibility but increase duplication

---

### AD-004: MessageType String in ApplicationMessage

**Decision**: ApplicationMessage has `MessageType` string property for runtime identification.

**Rationale**:
- Enables logging, debugging, and telemetry
- Allows switch-based routing without complex reflection
- Provides human-readable message type identifier
- Useful for serialization/deserialization

**Consequences**:
- ✅ Easy to log and debug
- ✅ Enables switch-based routing
- ⚠️ String-based (not type-safe)
- ⚠️ Need to coordinate string values

**Alternative Considered**: Use only type-based pattern matching
- Would be more type-safe but harder to log/serialize

---

### AD-005: Role as Abstract Property in ApplicationMessage

**Decision**: ApplicationMessage has abstract `Role` property that subtypes must define.

**Rationale**:
- Application messages can have different roles (User, Assistant, etc.)
- `ScenarioUserMessage` has User role
- Future `ScenarioAssistantMessage` has Assistant role
- Forces subtypes to explicitly define their LLM role

**Consequences**:
- ✅ Flexible - app messages can use any role
- ✅ Explicit - must be defined by subtype
- ⚠️ More complex than fixed role

**Alternative Considered**: ApplicationMessage always has custom role
- Would prevent scenarios from sending User-role messages

---

### AD-006: Stable Orchestrator API with Internal Routing

**Decision**: Orchestrator has 4 methods (one per origin), internal switch on subtypes.

**Rationale**:
- **Stable API**: Only 4 methods representing fundamental message origins
- **Extensible implementation**: Switch statement grows, but API doesn't
- **Clear caller intent**: Caller knows what origin category they're sending
- **Single Responsibility**: Each method handles one message origin category
- **Complete coverage**: 4 origins (Human, AI, Application, External Tools) cover all cases

**Consequences**:
- ✅ API stability - interface never changes
- ✅ Unlimited message type extensibility
- ⚠️ Switch statement grows (but compiler ensures exhaustiveness)
- ⚠️ Need to update switch for new subtypes

**Alternative Considered**: Single `ProcessMessageAsync(IMessage)` method
- Would be simpler but lose origin-based routing clarity

---

### AD-007: MessageTypeDiscriminator for Polymorphic Serialization

**Decision**: Add `MessageTypeDiscriminator` property to `IMessage` interface for serialization.

**Rationale**:
- **Polymorphic deserialization requires type information**: When loading saved messages, must instantiate correct concrete class before calling deserialize
- **Discriminator pattern is industry standard**: Used by Json.NET, Entity Framework, etc.
- **O(1) type lookup**: Dictionary-based type registry provides instant type resolution
- **Future-proof**: Enables conversation persistence without retrofitting later
- **Minimal cost**: ~30-50 bytes per message vs reliable serialization

**Format**: `"{OriginCategory}.{ConcreteType}"`
- Examples: `"User.Direct"`, `"Application.ScenarioUser"`, `"Llm.Text"`, `"Tool.Result"`

**Consequences**:
- ✅ Reliable polymorphic serialization/deserialization
- ✅ Standard industry pattern
- ✅ Maintainable - one dictionary entry per type
- ✅ Scalable - works with unlimited message types
- ⚠️ Additional property in domain model (~30-50 bytes per message)
- ⚠️ Need to coordinate discriminator string values

**Alternative Considered**: JSON wrapper pattern (type info separate from data)
- Pros: No property in domain model
- Cons: More complex serialization code, nested JSON structure
- Verdict: Discriminator property approach is simpler and more transparent

## Serialization and Persistence Strategy

### Overview

The four-tier hierarchy uses the **MessageTypeDiscriminator** property to enable polymorphic serialization and deserialization. This allows conversations to be saved and loaded while preserving the exact concrete message types.

### Discriminator Format

Format: `"{OriginCategory}.{ConcreteType}"`

Examples:
- `"User.Direct"` - DirectUserMessage
- `"Llm.Text"` - LlmTextMessage
- `"Llm.ToolCall"` - LlmToolCallMessage
- `"Application.ScenarioUser"` - ScenarioUserMessage
- `"Application.ScenarioAssistant"` - ScenarioAssistantMessage
- `"Tool.Result"` - ToolResultMessage
- `"Tool.Error"` - ToolErrorMessage

### Serialization Implementation

```csharp
public class MessageSerializer
{
    // Type registry for O(1) lookup
    private static readonly Dictionary<string, Type> TypeRegistry = new()
    {
        ["User.Direct"] = typeof(DirectUserMessage),
        ["Llm.Text"] = typeof(LlmTextMessage),
        ["Llm.ToolCall"] = typeof(LlmToolCallMessage),
        ["Application.ScenarioUser"] = typeof(ScenarioUserMessage),
        ["Application.ScenarioAssistant"] = typeof(ScenarioAssistantMessage),
        ["Application.ToolUpdate"] = typeof(ToolUpdateMessage),
        ["Tool.Result"] = typeof(ToolResultMessage),
        ["Tool.Error"] = typeof(ToolErrorMessage),
        ["Tool.Progress"] = typeof(ToolProgressMessage),
    };

    public string Serialize(IMessage message)
    {
        // Serialize using concrete type for all properties
        return JsonSerializer.Serialize(message, message.GetType(), new JsonSerializerOptions
        {
            WriteIndented = true
        });
    }

    public IMessage Deserialize(string json)
    {
        // Parse JSON to read discriminator
        var doc = JsonDocument.Parse(json);
        var discriminator = doc.RootElement.GetProperty("MessageTypeDiscriminator").GetString();

        if (string.IsNullOrEmpty(discriminator))
        {
            throw new InvalidOperationException("Message missing MessageTypeDiscriminator property");
        }

        // Lookup concrete type - O(1)
        if (!TypeRegistry.TryGetValue(discriminator, out var type))
        {
            throw new InvalidOperationException($"Unknown message type discriminator: {discriminator}");
        }

        // Deserialize to concrete type
        var message = (IMessage)JsonSerializer.Deserialize(json, type)!;
        return message;
    }

    public List<IMessage> DeserializeConversation(string json)
    {
        var messagesJson = JsonSerializer.Deserialize<JsonElement[]>(json);
        var messages = new List<IMessage>();

        foreach (var messageJson in messagesJson!)
        {
            var messageString = messageJson.GetRawText();
            messages.Add(Deserialize(messageString));
        }

        return messages;
    }
}
```

### Benefits of This Approach

1. **Simple and Standard**: Discriminator pattern is widely used (Json.NET, EF Core, etc.)
2. **Fast**: O(1) type lookup via dictionary
3. **Maintainable**: Adding new type = one line in registry
4. **Type-Safe**: Compiler ensures discriminator is defined on all message types
5. **Transparent**: Type information visible in JSON (great for debugging)
6. **No Magic**: No reflection, no guessing, explicit type mapping

### Type Registry Maintenance

When adding a new message type:

1. Define the concrete class:
   ```csharp
   public class NewFeatureMessage : ApplicationMessage
   {
       public override string MessageTypeDiscriminator => "Application.NewFeature";
       // ... properties and constructor
   }
   ```

2. Add to type registry:
   ```csharp
   TypeRegistry["Application.NewFeature"] = typeof(NewFeatureMessage);
   ```

3. That's it! Serialization and deserialization automatically work.

### Versioning and Migration

If message schema changes (e.g., adding properties, renaming fields):

**Option 1: Version in discriminator**

## Migration Path

### Phase 1: Define Message Hierarchy

1. Create abstract base classes:
   - `UserMessage` (abstract)
   - `LlmMessage` (abstract)
   - `ApplicationMessage` (abstract)

2. Create concrete types:
   - `DirectUserMessage : UserMessage`
   - `LlmTextMessage : LlmMessage`
   - `LlmToolCallMessage : LlmMessage`
   - `ScenarioUserMessage : ApplicationMessage`

### Phase 2: Update Orchestrator

1. Refactor existing `ProcessUserInputAsync()`:
   - Rename to `ProcessUserMessageAsync()`
   - Accept `UserMessage` parameter instead of string
   - Caller constructs `DirectUserMessage`

2. Add `ProcessApplicationMessageAsync()`
   - Accepts `ApplicationMessage`
   - Internal switch on message type
   - Calls shared processing logic

3. Add `ProcessLlmMessageAsync()` (if needed)

### Phase 3: Update Callers

1. **GUI Layer** (user input):
   ```csharp
   // Before
   orchestrator.ProcessUserInputAsync(inputText);

   // After
   var userMessage = new DirectUserMessage(inputText);
   orchestrator.ProcessUserMessageAsync(userMessage);
   ```

2. **ScenarioExecutor** (scenario messages):
   ```csharp
   // Before
   orchestrator.ProcessUserInputAsync(step.Content);

   // After
   var scenarioMessage = new ScenarioUserMessage(step.Content, step.Annotation);
   orchestrator.ProcessApplicationMessageAsync(scenarioMessage);
   ```

### Phase 4: Update Message Pipeline

1. Add pattern matching for new types:
   ```csharp
   public List<LLMMessage> ConvertToLLMMessages(List<IMessage> messages)

       foreach (var message in messages)
       {
           LLMMessage? llmMsg = message switch

   private LLMMessage ConvertScenarioUserMessage(ScenarioUserMessage msg)
   ```

   - No more `_pendingAutoMessages` dictionary
   - No more annotation tracking

## Trade-offs and Alternatives

### Alternative 1: Keep Flat Structure + Metadata

**Approach**: Keep flat message types, add metadata dictionary.

```csharp
class UserMessage : IMessage
{
    public Dictionary<string, object>? Metadata { get; }
}
```

**Pros**:
- ✅ Simpler hierarchy
- ✅ Fewer code changes

**Cons**:
- ❌ No type safety
- ❌ Runtime errors instead of compile-time
- ❌ Still need to handle in orchestrator
- ❌ Doesn't solve API growth problem

**Verdict**: ❌ Doesn't address core architectural issue

---

### Alternative 2: Single Orchestrator Method + Runtime Dispatch

**Approach**: One method, runtime type checking.

```csharp
interface IAgentOrchestrator
{
    ProcessMessageAsync(IMessage message);  // ← One method for everything
}
```

**Pros**:
- ✅ Simplest API (1 method)
- ✅ Maximum flexibility

**Cons**:
- ❌ Loses origin-based routing clarity
- ❌ No compile-time guidance for callers
- ❌ Complex internal dispatch logic
- ❌ Hard to understand what message types are valid

**Verdict**: ⚠️ Too generic, loses architectural clarity

---

### Alternative 3: Composition Over Inheritance

**Approach**: Messages contain origin metadata, no inheritance.

```csharp
class Message : IMessage
{
    public MessageOrigin Origin { get; }  // Enum: User/LLM/Application
    public string OriginDetails { get; }  // "scenario", "tool_update", etc.
}
```

**Pros**:
- ✅ Flat structure
- ✅ No inheritance complexity

**Cons**:
- ❌ Loses type safety
- ❌ Enum-based switching (less extensible)
- ❌ Can't enforce origin-specific properties
- ❌ Runtime checking instead of compile-time

**Verdict**: ⚠️ Simpler but less type-safe

---

### Alternative 4: Message Builders/Factories

**Approach**: Use factory pattern to create messages.

```csharp
interface IMessageFactory
{
    IMessage CreateUserMessage(string content);
    IMessage CreateScenarioMessage(string content, string annotation);
    IMessage CreateToolUpdateMessage(...);
}
```

**Pros**:
- ✅ Centralized message creation
- ✅ Can add validation

**Cons**:
- ❌ Doesn't address orchestrator API growth
- ❌ Still need orchestrator methods for each type
- ❌ Adds factory complexity
- ❌ Doesn't solve architectural issue

**Verdict**: ⚠️ Useful addition but not a replacement

## Recommendation

### ✅ RECOMMENDED: Four-Tier Message Hierarchy

**Implement the four-tier hierarchy with:**
1. Abstract base classes for message origins (UserMessage, LlmMessage, ApplicationMessage, ToolMessage)
2. Concrete subtypes for specific use cases (DirectUserMessage, ScenarioUserMessage, ToolResultMessage, etc.)
3. Stable 4-method orchestrator API (one per origin)
4. Internal switch-based routing on subtypes
5. MessageTypeDiscriminator for polymorphic serialization

**Why**:
- ✅ Solves **all identified problems** (API growth, type safety, extensibility)
- ✅ Clear **architectural model** (4 fundamental origin categories: Human, AI, Application, External Tools)
- ✅ **Future-proof** for scenarios, workflows, automation, tool integrations
- ✅ Follows **Clean Architecture** and **DDD** principles
- ✅ Type-safe and maintainable
- ✅ **Serializable** with discriminator pattern (industry standard)

**Trade-offs**:
- ⚠️ More complex than flat structure (acceptable for long-term stability)
- ⚠️ Requires updating multiple layers (one-time migration cost)
- ⚠️ Switch statements grow (but compiler-checked)
- ⚠️ Additional discriminator property (~30-50 bytes per message)

**Verdict**: The benefits far outweigh the costs. This is the right architectural foundation for a growing application with comprehensive serialization support.

### Testing Questions for Discussion

1. **Should we test abstract base classes directly?**
   - Recommendation: No, test through concrete implementations
   - Reason: Abstract classes can't be instantiated, and testing through subclasses provides better coverage

2. **How to handle testing of internal switch statements in orchestrator?**
   - Recommendation: Test observable behavior (messages added, LLM called) not implementation details
   - Reason: Allows refactoring switch to strategy pattern later without breaking tests

3. **Should serialization tests use real JSON files or inline strings?**
   - Recommendation: Inline strings for unit tests, real files for integration tests
   - Reason: Faster unit tests, integration tests catch file format issues

4. **Coverage target for message types vs orchestrator?**
   - Recommendation: 95% for message types (simple), 85% for orchestrator (complex)
   - Reason: Message types are straightforward, orchestrator has complex error paths
