# Critical Review: Three-Tier Message Hierarchy Architecture

**Date**: 2025-11-13
**Reviewer**: Critical Analysis
**Documents Reviewed**:
- `SCENARIO_USER_MESSAGE_SOLUTION_ELABORATION.md`
- `MESSAGE_ARCHITECTURE_REDESIGN.md`

## Executive Summary

The three-tier message hierarchy (UserMessage/LlmMessage/ApplicationMessage) is a **significant architectural improvement** over the flat structure, but several critical issues need addressing before implementation:

### Critical Issues (Must Fix)
1. **Role property conflicts** - ApplicationMessage has abstract Role, breaking IMessage contract
2. **Incomplete LlmMessage design** - Doesn't account for existing AssistantToolCallMessage
3. **Missing persistence strategy** - No serialization/deserialization design
4. **Unclear boundary between User/Application** - When is a message "user" vs "application"?

### Significant Concerns (Should Fix)
5. **Switch statement maintainability** - Will grow to 20+ cases without governance
6. **Testing strategy undefined** - How to test abstract base classes?
7. **Migration path underspecified** - Breaking changes not fully analyzed
8. **Performance implications not measured** - Type checking overhead unclear

### Minor Issues (Consider)
9. **Naming inconsistencies** - DirectUserMessage vs LlmTextMessage patterns differ
10. **Documentation gaps** - When to create new type vs extend existing?

## CRITICAL ISSUE #1: Role Property Conflicts in ApplicationMessage

### Problem

```csharp
// From MESSAGE_ARCHITECTURE_REDESIGN.md
public abstract class ApplicationMessage : IMessage
{
    public abstract MessageRole Role { get; } // ← Abstract property
}

public interface IMessage
{
    MessageRole Role { get; } // ← Interface property (likely not abstract)
}
```

**Issue**: If `IMessage.Role` is a concrete getter, making it abstract in ApplicationMessage violates the interface contract.

**Why This Matters**:
- C# doesn't allow abstract implementation of interface properties unless interface itself is abstract
- Compiler will reject this code
- Creates confusion about who determines the role

### Root Cause

ApplicationMessage tries to be **both** a base class (with shared implementation) **and** a variant type (with different roles per subtype). These goals conflict.

### How to Fix

**Option A: Remove Role from ApplicationMessage, keep in IMessage**

```csharp
public interface IMessage
{
    MessageRole Role { get; }
    // ... other properties
}

public abstract class ApplicationMessage : IMessage
{
    // Subtype must implement Role
    public abstract MessageRole Role { get; }

    // Shared properties
    public Guid Id { get; }
    public string Content { get; }
    public DateTime Timestamp { get; }
    public MessageContextStatus ContextStatus { get; set; }
    public string MessageType { get; }
}

public class ScenarioUserMessage : ApplicationMessage
{
    public override MessageRole Role => MessageRole.User; // ← Concrete implementation
}
```

**Pros**:
- ✅ Compiles correctly
- ✅ Forces subtypes to define role explicitly
- ✅ Follows Liskov Substitution Principle

**Cons**:
- ⚠️ Each subtype must implement Role (but that's intentional)

**Option B: Role as constructor parameter in ApplicationMessage**

```csharp
public abstract class ApplicationMessage : IMessage
{
    public MessageRole Role { get; } // ← Concrete, set by constructor

    protected ApplicationMessage(string content, MessageRole role, string messageType)
    {
        Role = role;
        Content = content;
        MessageType = messageType;
        // ...
    }
}

public class ScenarioUserMessage : ApplicationMessage
{
    public ScenarioUserMessage(string content, string? annotation = null)
        : base(content, MessageRole.User, "scenario_user_message") // ← Pass role up
    {
        Annotation = annotation;
    }
}
```

**Pros**:
- ✅ Less boilerplate in subtypes
- ✅ Clear in constructor what role is used
- ✅ Compiler ensures role is set

**Cons**:
- ⚠️ Subtype could accidentally pass wrong role
- ⚠️ Less explicit at class level what role is used

### Recommendation

**Use Option A** - Abstract property that subtypes override. This makes the role **explicit and visible** at the class definition level, not buried in constructor calls.

## CRITICAL ISSUE #2: Incomplete LlmMessage Design

### Problem

The existing codebase has:
- `AssistantMessage` - Text responses from LLM
- `AssistantToolCallMessage` - LLM responses with tool calls
- `ToolResultMessage` - Results from tool execution

**The proposal only mentions**:
- `LlmTextMessage` - Text responses
- `LlmToolCallMessage` - Tool call responses

**Missing**:
- Where does `ToolResultMessage` fit?
- Is it LlmMessage (no, it's not from LLM)?
- Is it ApplicationMessage (generated by tool execution)?
- Is it a separate category entirely?

### Why This Matters

Tool execution is **not originated by LLM, User, or Application logic**. It's originated by **tool infrastructure in response to LLM tool calls**.

This reveals a **4th origin category** not accounted for: **ToolMessage**

### How to Fix

**Option A: Add ToolMessage as 4th category**

```csharp
/// <summary>
/// Messages originating from tool execution infrastructure.
/// Generated by tool calls, but not by the LLM itself.
/// </summary>
public abstract class ToolMessage : IMessage
{
    public MessageRole Role => MessageRole.Tool;
    public Guid ToolCallId { get; }
    public string ToolName { get; }
    // ...
}

public class ToolResultMessage : ToolMessage
{
    public string Result { get; }
    public bool IsError { get; }
}

public class ToolErrorMessage : ToolMessage
{
    public string ErrorMessage { get; }
    public Exception? Exception { get; }
}
```

**Orchestrator API becomes**:
```csharp
interface IAgentOrchestrator
{
    ProcessUserMessageAsync(UserMessage msg);
    ProcessApplicationMessageAsync(ApplicationMessage msg);
    ProcessLlmMessageAsync(LlmMessage msg);
    ProcessToolMessageAsync(ToolMessage msg); // ← 4th method
}
```

**Pros**:
- ✅ Accurate categorization of tool results
- ✅ Explicit tool message handling
- ✅ Future tool types (streaming, progress) fit naturally

**Cons**:
- ❌ Violates "3-method API" principle
- ⚠️ Is 4 methods acceptable? Where does it stop?

**Option B: ToolResultMessage as ApplicationMessage subtype**

```csharp
public class ToolResultMessage : ApplicationMessage
{
    public override MessageRole Role => MessageRole.Tool;
    public Guid ToolCallId { get; }
    public string ToolName { get; }
    // ...
}
```

**Pros**:
- ✅ Keeps 3-method API
- ✅ Tools are "application infrastructure"

**Cons**:
- ⚠️ Philosophically questionable (is tool result "application-generated"?)
- ⚠️ Conflates application logic with infrastructure responses

**Option C: Keep flat for tool messages**

```csharp
// Tool messages don't inherit from origin hierarchy
public class ToolResultMessage : IMessage
{
    // Direct IMessage implementation
}

interface IAgentOrchestrator
{
    ProcessUserMessageAsync(UserMessage msg);
    ProcessApplicationMessageAsync(ApplicationMessage msg);
    ProcessLlmMessageAsync(LlmMessage msg);
    // Tool messages added directly to conversation, no processing method
}
```

**Pros**:
- ✅ Keeps 3-method API
- ✅ Recognizes tool results are different from origin categories
- ✅ Simple

**Cons**:
- ❌ Inconsistent - some messages in hierarchy, some flat
- ❌ Loses categorization benefits for tools

### Recommendation

**Option B with clear documentation** - Treat tools as application infrastructure. Tool execution is application-level functionality (MCP integration, tool manager, etc.), so tool results are application-generated messages.

**Document clearly**:
```csharp
/// <summary>
/// Messages generated by the application itself.
/// This includes:
/// - Teaching scenarios (ScenarioUserMessage)
/// - Tool execution results (ToolResultMessage) ← Explicit
/// - System notifications (ToolUpdateMessage)
/// - Automated workflows (WorkflowMessage)
/// </summary>
public abstract class ApplicationMessage : IMessage { }
```

## CRITICAL ISSUE #3: Missing Persistence Strategy

### Problem

The proposal doesn't address:
1. **Serialization** - How are messages saved/loaded?
2. **Polymorphic deserialization** - How to reconstruct concrete types from JSON/DB?
3. **Version compatibility** - What happens when message schema changes?

### Why This Matters

If conversations are persisted (highly likely future requirement), you need:
- Type discriminators in serialized data
- Version fields for schema evolution
- Migration strategy when adding new message types

**Without this**, you'll face:
```json
// Saved conversation - which concrete type is this?
{
  "id": "123",
  "role": "User",
  "content": "Hello",
  "timestamp": "2025-11-13T10:00:00Z"
  // ← Missing: What concrete type? DirectUserMessage? ScenarioUserMessage?
}
```

### How to Fix

**Add type discriminator to IMessage**:

```csharp
public interface IMessage
{
    Guid Id { get; }
    MessageRole Role { get; }
    string Content { get; }
    DateTime Timestamp { get; }
    MessageContextStatus ContextStatus { get; set; }

    /// <summary>
    /// Type discriminator for serialization/deserialization.
    /// Format: "{OriginCategory}.{ConcreteType}"
    /// Examples: "User.Direct", "Application.ScenarioUser", "Llm.Text"
    /// </summary>
    string MessageTypeDiscriminator { get; }
}
```

**In base classes**:

```csharp
public abstract class ApplicationMessage : IMessage
{
    // Default implementation - subclasses can override
    public virtual string MessageTypeDiscriminator => $"Application.{GetType().Name}";

    // OR explicit in each subtype:
}

public class ScenarioUserMessage : ApplicationMessage
{
    public override string MessageTypeDiscriminator => "Application.ScenarioUser";
}
```

**Serialization**:

```csharp
public class MessageSerializer
{
    private static readonly Dictionary<string, Type> TypeMap = new()
    {
        ["User.Direct"] = typeof(DirectUserMessage),
        ["Application.ScenarioUser"] = typeof(ScenarioUserMessage),
        ["Llm.Text"] = typeof(LlmTextMessage),
        // ...
    };

    public string Serialize(IMessage message)
    {
        return JsonSerializer.Serialize(message, message.GetType());
    }

    public IMessage Deserialize(string json)
    {
        var doc = JsonDocument.Parse(json);
        var discriminator = doc.RootElement.GetProperty("MessageTypeDiscriminator").GetString();
        var type = TypeMap[discriminator];
        return (IMessage)JsonSerializer.Deserialize(json, type)!;
    }
}
```

### Recommendation

**Add MessageTypeDiscriminator to design now**, even if persistence is future work. Retrofitting later is painful.

**Document serialization strategy** in architecture proposal.

## CRITICAL ISSUE #4: Unclear User/Application Boundary

### Problem

When does a message belong to `UserMessage` vs `ApplicationMessage`?

**Example Confusion**:
- Scenario sends message with User role → ApplicationMessage (ScenarioUserMessage)
- User types message → UserMessage (DirectUserMessage)
- User uploads file, system generates "File uploaded: foo.txt" → UserMessage or ApplicationMessage?
- User clicks "Regenerate response" → UserMessage or ApplicationMessage?

**The boundary is fuzzy** because "user-initiated" vs "user-typed" are different concepts.

### Why This Matters

Without clear guidelines, developers will:
- Inconsistently categorize messages
- Create the wrong subtypes
- Pollute wrong categories

Example problematic code:
```csharp
// Is this UserMessage or ApplicationMessage?
var msg = new FileUploadConfirmationMessage("File uploaded: " + filename);

// Developer 1: "User initiated it, so UserMessage"
public class FileUploadConfirmationMessage : UserMessage { }

// Developer 2: "System generated it, so ApplicationMessage"
public class FileUploadConfirmationMessage : ApplicationMessage { }

// ← Inconsistent!
```

### How to Fix

**Define clear boundary rules**:

| Message Origin | Category | Rule |
|----------------|----------|------|
| User typed text in chat | UserMessage | Direct human input to chat interface |
| User clicked UI button that sends message | ApplicationMessage | System translated user action into message |
| Scenario/workflow sends message | ApplicationMessage | Application logic generated content |
| LLM responded | LlmMessage | LLM API returned response |
| Tool executed | ApplicationMessage | Tool infrastructure generated result |

**Document in architecture**:

```csharp
/// <summary>
/// Messages originating from direct human input to the chat interface.
///
/// RULE: Use UserMessage ONLY when:
/// - User typed text into chat input box
/// - User used voice input that was transcribed
/// - User pasted text into chat
///
/// DO NOT use UserMessage for:
/// - System-generated messages (even if user-initiated)
/// - File upload notifications
/// - Button click results
/// - Scenario messages (even with User role)
///
/// If in doubt, use ApplicationMessage.
/// </summary>
public abstract class UserMessage : IMessage { }
```

### Recommendation

**Add "Decision Guide" section** to architecture document with clear categorization rules and examples.

## SIGNIFICANT CONCERN #5: Switch Statement Maintainability

### Problem

The proposal says:
> Internal switch on message subtypes

But doesn't address:
- What happens when switch has 20+ cases?
- How to ensure all cases are handled?
- How to avoid code duplication across cases?

**Example of future problem**:

```csharp
public async IAsyncEnumerable<StreamingResponseChunk> ProcessApplicationMessageAsync(
    ApplicationMessage message,
    CancellationToken cancellationToken = default)
{
    _conversationManager.AddMessage(message);

    switch (message)
    {
        case ScenarioUserMessage scenarioMsg:
            LogEvent("Scenario", scenarioMsg.Annotation ?? "");
            break;
        case ScenarioAssistantMessage scenarioAsst:
            LogEvent("ScenarioAssistant", scenarioAsst.Annotation ?? "");
            yield break; // ← Different behavior!
        case ToolResultMessage toolResult:
            LogEvent("ToolResult", toolResult.ToolName);
            break;
        case ToolUpdateMessage toolUpdate:
            LogEvent("ToolUpdate", string.Join(", ", toolUpdate.AddedTools));
            break;
        case WorkflowMessage workflow:
            LogEvent("Workflow", $"{workflow.WorkflowId}/{workflow.StepIndex}");
            break;
        case ContextInjectionMessage context:
            LogEvent("Context", context.Source);
            break;
        case ProgressUpdateMessage progress:
            LogEvent("Progress", $"{progress.Percentage}%");
            break;
        // ... 15 more cases
        default:
            LogEvent("ApplicationMessage", message.MessageType);
            break;
    }

    // ← Some messages should trigger LLM loop, some shouldn't!
    // How to determine?

    if (message is ScenarioAssistantMessage)
        yield break; // Don't process, it IS the response

    await foreach (var chunk in ProcessStreamingToolLoopAsync(0, cancellationToken))
    {
        yield return chunk;
    }
}
```

**Issues**:
1. **Scaling**: 20+ cases = 100+ lines of switch
2. **Duplication**: Many cases do similar logging
3. **Complex control flow**: Some messages trigger LLM, some don't
4. **Hard to test**: Need test for each case combination

### How to Fix

**Option A: Strategy Pattern**

```csharp
public interface IApplicationMessageHandler<T> where T : ApplicationMessage
{
    Task<MessageHandlingResult> HandleAsync(T message, CancellationToken cancellationToken);
}

public class ScenarioUserMessageHandler : IApplicationMessageHandler<ScenarioUserMessage>
{
    public async Task<MessageHandlingResult> HandleAsync(
        ScenarioUserMessage message,
        CancellationToken cancellationToken)
    {
        LogEvent("Scenario", message.Annotation ?? "");
        return MessageHandlingResult.TriggerLlmLoop;
    }
}

public class ScenarioAssistantMessageHandler : IApplicationMessageHandler<ScenarioAssistantMessage>
{
    public async Task<MessageHandlingResult> HandleAsync(
        ScenarioAssistantMessage message,
        CancellationToken cancellationToken)
    {
        LogEvent("ScenarioAssistant", message.Annotation ?? "");
        return MessageHandlingResult.SkipLlmLoop; // ← Explicit behavior
    }
}

// In orchestrator
public async IAsyncEnumerable<StreamingResponseChunk> ProcessApplicationMessageAsync(
    ApplicationMessage message,
    CancellationToken cancellationToken = default)
{
    _conversationManager.AddMessage(message);

    var handler = _handlerFactory.GetHandler(message.GetType());
    var result = await handler.HandleAsync((dynamic)message, cancellationToken);

    if (result.TriggerLlmLoop)
    {
        await foreach (var chunk in ProcessStreamingToolLoopAsync(0, cancellationToken))
        {
            yield return chunk;
        }
    }
}
```

**Pros**:
- ✅ Each message type has dedicated handler
- ✅ Easy to test handlers individually
- ✅ No giant switch statement
- ✅ Explicit behavior per message type

**Cons**:
- ⚠️ More classes (handler per message type)
- ⚠️ Need handler registration/discovery
- ⚠️ More abstraction

**Option B: Virtual method on ApplicationMessage**

```csharp
public abstract class ApplicationMessage : IMessage
{
    // ...

    /// <summary>
    /// Determines if this message should trigger LLM processing.
    /// Override in subtypes to customize behavior.
    /// </summary>
    public virtual bool ShouldTriggerLlmLoop => true;

    /// <summary>
    /// Called when message is added to conversation.
    /// Override for message-specific logging/handling.
    /// </summary>
    public virtual Task OnAddedToConversationAsync(ILogger logger)
    {
        logger.LogInformation($"ApplicationMessage: {MessageType}");
        return Task.CompletedTask;
    }
}

public class ScenarioUserMessage : ApplicationMessage
{
    public override bool ShouldTriggerLlmLoop => true;

    public override Task OnAddedToConversationAsync(ILogger logger)
    {
        logger.LogInformation($"Scenario: {Annotation ?? Content}");
        return Task.CompletedTask;
    }
}

public class ScenarioAssistantMessage : ApplicationMessage
{
    public override bool ShouldTriggerLlmLoop => false; // ← It IS the response

    public override Task OnAddedToConversationAsync(ILogger logger)
    {
        logger.LogInformation($"ScenarioAssistant: {Annotation ?? Content}");
        return Task.CompletedTask;
    }
}

// In orchestrator - dramatically simplified
public async IAsyncEnumerable<StreamingResponseChunk> ProcessApplicationMessageAsync(
    ApplicationMessage message,
    CancellationToken cancellationToken = default)
{
    _conversationManager.AddMessage(message);
    await message.OnAddedToConversationAsync(_logger);

    if (message.ShouldTriggerLlmLoop)
    {
        await foreach (var chunk in ProcessStreamingToolLoopAsync(0, cancellationToken))
        {
            yield return chunk;
        }
    }
}
```

**Pros**:
- ✅ No switch statement at all
- ✅ Behavior defined at message type level
- ✅ Simple orchestrator code
- ✅ Easy to understand per-message behavior

**Cons**:
- ⚠️ Behavior spread across message classes (less centralized)
- ⚠️ Harder to see all message handling in one place

### Recommendation

**Use Option B** - Virtual methods on ApplicationMessage. This:
- Eliminates switch statement entirely
- Keeps behavior with message type definition
- Scales to unlimited message types
- Follows Open/Closed Principle (open for extension, closed for modification)

**Add to proposal**:
```csharp
public abstract class ApplicationMessage : IMessage
{
    public virtual bool ShouldTriggerLlmLoop => true;
    public virtual Task OnAddedToConversationAsync(ILogger logger) => Task.CompletedTask;
}
```

## SIGNIFICANT CONCERN #7: Migration Path Underspecified

### Problem

The proposal says "Phase 1, Phase 2..." but doesn't address:
- **Breaking changes**: Existing code that assumes `UserMessage` is concrete
- **Serialized data**: What happens to saved conversations?

**Add detailed migration analysis**:

#### Breaking Changes

**1. UserMessage becomes abstract**

```csharp
// Before (concrete)
public class UserMessage : IMessage { }

// After (abstract)
public abstract class UserMessage : IMessage { }
```

**Impact**: Any code doing `new UserMessage(...)` will break.

**Search Required**:

```csharp
// After
IAsyncEnumerable<StreamingResponseChunk> ProcessUserMessageAsync(UserMessage message, CancellationToken ct = default)
```

**Impact**: All callers must change.

**Fix**:
```csharp
// Before
await orchestrator.ProcessUserInputAsync(userInput);

// After
var message = new DirectUserMessage(userInput);
await foreach (var chunk in orchestrator.ProcessUserMessageAsync(message, ct))
{
    // Handle streaming
}
```

**3. Pattern matching on messages**

```csharp
// Before - might assume UserMessage is one concrete type

    // ...
}

{
```

**Impact**: Any code pattern matching on `UserMessage` might have incorrect assumptions.

**Search Required**:


```csharp
}
```

## SIGNIFICANT CONCERN #8: Performance Implications Not Measured

### Problem

The proposal doesn't analyze:
- Overhead of type hierarchy (virtual method calls)
- Impact of pattern matching in hot paths
- Memory implications of additional properties

### Relevant Code Paths

**Hot path 1: Message processing**
- Every message goes through orchestrator routing
- Pattern matching or virtual calls happen for each message
- Pipeline conversion happens for each message

**Hot path 2: UI rendering**
- `UIMessage.FromDomainMessage()` called for every message on every refresh
- Pattern matching on message types
- CSS class computation

### How to Fix

**Add performance considerations section**:

#### Expected Overhead

1. **Virtual method calls**: ~1-2ns per call (negligible)
2. **Pattern matching**: ~5-10ns per match (negligible for <100 messages)
3. **Additional properties**: `string MessageType` + `string? Annotation` = ~40-80 bytes per message

**For typical conversation (100 messages)**:
- Extra memory: ~4-8 KB
- Extra CPU: <1 microsecond total
- **Verdict**: Negligible impact

#### Potential Concerns

**1. Large conversation (10,000 messages)**:
- Extra memory: ~400-800 KB
- Pattern matching overhead: ~100 microseconds
- **Verdict**: Still negligible

**2. RefreshMessages called frequently**:
- If UI refreshes conversation 100 times/second (unrealistic)
- Pattern matching: 10ms per refresh
- **Verdict**: Only a concern if refresh rate is abnormally high

### Recommendation

**Add performance analysis** to proposal stating expected overhead is negligible for realistic conversation sizes.

**If concerned, add benchmarking**:
```csharp

{
    [TestMethod]
    public void Benchmark_MessageProcessing_1000Messages()
```

## MINOR ISSUE #9: Naming Inconsistencies

### Problem

Naming patterns are inconsistent:

- `DirectUserMessage` - Adjective + Origin + "Message"
- `LlmTextMessage` - Origin + Type + "Message"
- `ScenarioUserMessage` - Context + Role + "Message"

**Confusion**:
- Why "Direct" for user but not "Direct" for LLM?
- Why "Text" for LLM but not for User (isn't DirectUserMessage also text)?
- Why "ScenarioUser" instead of "ScenarioUserRole" or "ApplicationUserRole"?

### How to Fix

**Option A: Consistent Origin + Type pattern**

```csharp
// User origin
UserInputMessage      // User typed input (was DirectUserMessage)
UserVoiceMessage      // Future: voice input

// LLM origin
LlmTextMessage        // Text response (stays same)
LlmToolCallMessage    // Tool call response (stays same)

// Application origin
ApplicationScenarioUserMessage      // Scenario with user role (was ScenarioUserMessage)
ApplicationScenarioAssistantMessage // Scenario with assistant role
ApplicationToolResultMessage        // Tool result (was ToolResultMessage)
ApplicationToolUpdateMessage        // Tool update notification
```

**Pros**:
- ✅ Origin is always first
- ✅ Type/context is second
- ✅ Consistent pattern

**Cons**:
- ❌ Very long names (`ApplicationScenarioUserMessage`)
- ❌ ApplicationMessage prefix is redundant (they already inherit from it)

**Option B: Consistent Type + Origin pattern**

```csharp
// User origin
TextUserMessage       // User typed text (was DirectUserMessage)
VoiceUserMessage      // Future: voice input

// LLM origin
TextLlmMessage        // Text response (was LlmTextMessage)
ToolCallLlmMessage    // Tool call response (was LlmToolCallMessage)

// Application origin
ScenarioUserRoleMessage     // Scenario with user role
ScenarioAssistantRoleMessage // Scenario with assistant role
ToolResultMessage           // Tool result
ToolUpdateMessage           // Tool update notification
```

**Pros**:
- ✅ Type/purpose first (more readable)
- ✅ Reasonable name lengths
- ✅ Consistent pattern

**Cons**:
- ⚠️ Origin not always at same position (UserMessage, LlmMessage, but Message for Application)

**Option C: Keep current, document conventions**

Accept that different categories have different naming conventions:
- **UserMessage**: Adjective describing user type (Direct, Voice, etc.)
- **LlmMessage**: Content type (Text, ToolCall, etc.)
- **ApplicationMessage**: Context/purpose (Scenario, ToolResult, ToolUpdate, etc.)

Document in code comments:
```csharp
/// <summary>
/// Naming convention: {Adjective}UserMessage
/// Examples: DirectUserMessage, VoiceUserMessage
/// </summary>
public abstract class UserMessage : IMessage { }

/// <summary>
/// Naming convention: Llm{ContentType}Message
/// Examples: LlmTextMessage, LlmToolCallMessage
/// </summary>
public abstract class LlmMessage : IMessage { }

/// <summary>
/// Naming convention: {Context}{Role?}Message
/// Examples: ScenarioUserMessage, ToolResultMessage, ToolUpdateMessage
/// </summary>
public abstract class ApplicationMessage : IMessage { }
```

### Recommendation

**Option C** - Accept different conventions per category, document clearly. Consistency within each category is more important than consistency across categories.

## MINOR ISSUE #10: Documentation Gaps

### Problem

The proposal doesn't clearly answer:
- **When to create new message type vs extend existing?**
- **How to decide between User/Application for edge cases?**
- **What properties should go in base class vs subtype?**

### How to Fix

**Add "Developer Guidelines" section**:

#### When to Create New Message Type

**Create new subtype if**:
- ✅ Message has distinct properties (e.g., Annotation, ToolCallId)
- ✅ Message requires different UI rendering
- ✅ Message has different processing logic (e.g., ShouldTriggerLlmLoop = false)
- ✅ Message represents distinct domain concept

**DON'T create new subtype if**:
- ❌ Only difference is content (use same type with different content)
- ❌ Only difference is metadata for analytics (use tags/properties)
- ❌ Temporary/experimental feature (add property to existing type first)

**Examples**:

```csharp
// ✅ GOOD - Distinct concept, different properties
public class ScenarioUserMessage : ApplicationMessage
{
    public string? Annotation { get; } // ← New property
    public override bool ShouldTriggerLlmLoop => true; // ← Different behavior
}

// ❌ BAD - Just different content, no new properties/behavior
public class WelcomeMessage : UserMessage { }  // ← Don't do this!
// Instead: new DirectUserMessage("Welcome!") // ← Use existing type
```

#### Properties in Base Class vs Subtype

**Base class properties**:
- ✅ Required by IMessage interface (Id, Role, Content, etc.)
- ✅ Used by >50% of subtypes
- ✅ Fundamental to message concept

**Subtype properties**:
- ✅ Specific to this message type only
- ✅ Optional/nullable (not all messages need it)
- ✅ Domain-specific (e.g., ToolCallId, Annotation)

**Example**:

```csharp
// Base class - common properties
public abstract class ApplicationMessage : IMessage
{
    public Guid Id { get; }
    public string Content { get; }
    public DateTime Timestamp { get; }
    public string MessageType { get; }
    // ← Don't add Annotation here - only scenarios need it
}

// Subtype - specific properties
public class ScenarioUserMessage : ApplicationMessage
{
    public string? Annotation { get; } // ← Scenario-specific
}
```
